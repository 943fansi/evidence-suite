# r5: External Expert Review（外部专家评审 · 全局阶段 8）
> 服务全局管线 Stage 8（外部专家评审，审查门 r5，写作者侧对应 w6 提交）。

**Agent**: External (DeepSeek/GPT/ChatGPT — run multiple for parallel reviews)  
**Input**: `11_定稿.md`  
**Output**: `12_{agent}_外部专家提示词.txt` → `12_外部专家意见.md`

## 外部 API 不可用时的回退（重要）

发送给外部 agent 的**就是下面的 prompt 模板本身**。若当前环境**外部生成 API 不可用**，当前 assistant 本地执行本阶段时回退为**自评**：

1. 本地按下方 12 个审查维度 + 专家角色（`${SUITE_ROOT}/shared/references/expert_roles/index.md`）对 `11_定稿.md` 逐项评审。
2. 以同一 Markdown 结构输出评审意见，落盘 `12_外部专家意见.md`，并在文件头部注明"（本地自评回退，非真实外部专家）"。
3. 若用户明确要求真实外部评审而工具不可用，明确告知受阻，**不要**伪造专家署名。

## Prompt Template

```
请你作为"外部专家评审组"，审阅《{topic} {target_document}》。

输入材料包括：11_定稿.md

评审角色设定：
请分别从以下专家视角进行审查（角色选择参考 `${SUITE_ROOT}/shared/references/expert_roles/index.md` 按 topic 领域匹配）：
1. 领域专家（学科/技术核心）
2. 实践/应用专家（落地可行性）
3. 方法论/评估专家（研究设计严谨性）
4. 标准/合规专家（如适用）
5. 资源/实施专家（如适用）
6. 成果转化/推广专家（如适用）

> 对教育/社科类文档，跳过"资源/实施"中涉及硬件设备/供应商的内容。
> 对纯理论型论文，部分角色可合并。

重要要求：
1. 不要重写方案全文。
2. 不要新增未经输入材料支持的外部事实。
3. 不要泛泛表扬。
4. 重点指出问题、风险、缺口和可改进点。
5. 所有批评意见都要具体到章节、表述、指标、证据或逻辑。
6. 对无法判断的问题，标记为"需补充材料"，不要自行推断。
7. 评审意见要模拟真实科研项目外部评审口径，表达专业、克制、直接。

请重点审查以下方面：

一、选题与立项必要性
1. 选题是否具有明确工程需求或应用场景？
2. 立项背景是否有政策、行业、技术或安全需求支撑？
3. 是否存在"需求描述过泛、痛点不够具体"的问题？

二、国内外研究现状
1. 是否区分了国际研究、国内研究、实践应用、标准规范？
2. 是否准确呈现已有技术水平，是否存在夸大技术空白？
3. 是否明确指出本项目与已有研究的差距和切入点？

三、项目目标与指标
1. 总体目标是否清晰？
2. 具体指标是否可量化、可测试、可验收？
3. 指标是否区分"已有案例数据、对标指标、项目拟定指标、待验证指标"？
4. 是否存在指标过高、过低或缺少依据的问题？

四、研究内容与技术路线
1. 研究内容是否围绕核心问题展开？技术路线是否闭合？
2. 关键技术之间的依赖关系是否明确？
3. 是否存在技术路线超出资料支撑或项目周期能力的问题？

五、创新性
1. 创新点是否具体？是否与现有技术差距对应？
2. 是否存在把"已有方法整合"包装成"核心原创创新"的问题？

六、证据链与引用质量
1. 正文关键结论是否都有 [Sx] 引用？
2. 是否存在弱来源支撑强结论的问题？
3. 是否存在 C 类资料被用作核心依据的问题？

七、资源与选型（工程/设备类文档填写；教育/社科类可跳过）
1. 选型是否与技术路线匹配？
2. 是否存在选型过早或过于确定的问题？
3. 是否有明确报价依据？

八、风险分析与保障措施
1. 风险是否覆盖技术、工程、数据、供应链、合规、预算、进度？
2. 应对措施是否具体？是否设置降级方案或替代路线？

九、实施计划与组织管理
1. 进度安排是否合理？阶段任务是否有明确里程碑？

十、测试验证与验收
1. 是否有针对性的验证方案？
2. 是否存在"有指标无验证方法"的问题？

十一、成果产出与转化
1. 预期成果是否与研究内容对应？
2. 是否存在成果承诺过多的问题？

十二、需补充调研清单
1. 是否完整覆盖关键缺口？是否按优先级排序？

请输出 Markdown：
```
